Most API problems do not arrive as dramatic architecture failures. They arrive as small compromises: one serializer doing too much, one endpoint leaking business rules, one queryset that was fine with ten rows and miserable with ten thousand.

At KEHEM, we try to make backend decisions boring in the best possible way. A good Django REST API should be understandable in review, predictable in production, and easy for the next developer to extend without becoming a detective.

1. Sharp serializer boundaries

Serializers are excellent at validation and representation. They become painful when they quietly absorb product policy, permission logic, notification behavior, and reporting concerns.

  • Use separate serializers for list, detail, create, and update when the shape or rules differ.
  • Move orchestration into service functions when the endpoint has meaningful business workflow.
  • Keep computed fields cheap, explicit, and visible in review.
A serializer should answer: â€œWhat shape is valid here?â€ It should not become the hidden control room for the whole product.

2. Permissions first

Permission checks should be boring, direct, and early. We prefer an explicit permission layer before object access, then queryset-level scoping as a second line of defense.

class ProjectViewSet(ModelViewSet):
    permission_classes = [IsAuthenticated, BelongsToActiveWorkspace]

    def get_queryset(self):
        return Project.objects.filter(
            workspace__members=self.request.user
        ).select_related("owner")

This keeps the API honest even when new actions are added later. The goal is not cleverness; it is reducing the number of places a future mistake can hide.

3. Querysets are contracts

Database performance is not a cleanup task for â€œlater.â€ Query behavior is part of the endpoint contract. If the API promises a dashboard response, the queryset has to be designed for dashboard conditions.

  • Use select_related and prefetch_related intentionally, not reactively.
  • Keep list endpoints lean; detail endpoints can carry more context.
  • Add indexes based on real filter and ordering patterns, not guesswork.

4. Make errors human

Good error responses reduce support time. We structure errors so frontend developers, QA, and product owners can understand what happened without reading server logs every time.

{
  "error": {
    "code": "subscription_limit_reached",
    "message": "This workspace has reached its active project limit.",
    "field": "workspace"
  }
}

Readable errors make the product feel more stable because the interface can respond with clarity instead of generic failure states.

5. Test behavior

We keep endpoint tests focused on the product promise: who can access it, what input is valid, what response shape is guaranteed, and what side effects occur.

  • Test permission boundaries with multiple user roles.
  • Test list endpoints for filtering, ordering, and pagination behavior.
  • Test important failure states, especially billing, ownership, and data visibility.

6. See production clearly

Production APIs need enough instrumentation to explain themselves. We like structured logs around important workflow events, request IDs across service boundaries, and metrics for slow endpoints before launch.

That does not mean every small project needs enterprise ceremony. It means the team should be able to answer: â€œWhat failed, for whom, and why?â€ without guessing.

Clean up the backend.

We design, refactor, and ship Django systems that feel calm under real users: clear API contracts, thoughtful performance, and fewer production surprises.
